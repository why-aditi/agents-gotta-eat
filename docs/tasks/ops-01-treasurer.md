# Task: ops-01 Treasurer agent and PayPal reconciliation

Status: approved Oct 27, 2026. Builds on pm-04 (`paypal` client, payments, escrow, webhooks), pm-04c (receivables), admin-01 (admin tabs, ledger reads, reconcile), pm-06 (`llm` module), sub-01 (merged before this starts).

Spec sections: "PayPal integration" (Agent Toolkit: the Treasurer agent; Webhooks handled), `docs/tasks/paypal-spike.md` findings (toolkit `get_order` and `list_transactions` work; invoicing returns 403; no payouts or authorizations tools), "Testing" (Pre-submission: ledger reconciliation clean against PayPal sandbox), "Security" (untrusted text). Architecture: "Observability" (admin dashboard: PayPal calls with status, webhook events, reconciliation report green or red).

## Decisions

| Area | Decision |
| --- | --- |
| Module boundary | Only the `paypal` module calls PayPal. New `paypal/toolkit.ts` wraps `@paypal/agent-toolkit` (pinned `1.11.0`, OpenAI flavour's `handleToolCall` as in `spikes/paypal/src/09-toolkit.ts`; fresh toolkit per call so each gets its own `PayPal-Request-Id`; sandbox only, refusing any non-sandbox base like the client does) and exposes `toolkitGetOrder(orderId)` and `toolkitListTransactions({ start, end })`. The toolkit always targets `api-m.sandbox.paypal.com`; in tests and e2e (fake PayPal base on localhost) the wrapper falls back to the existing typed client's direct calls (`GET /v2/checkout/orders/{id}`, `GET /v1/reporting/transactions`) so the fake can serve them. Add direct reads to the client too: `getCapture`, `getAuthorization`, `getPayoutItem` (if not present) |
| PayPal call log | Migration `0012_paypal_calls`: `paypal_calls` (`id` bigserial, `method`, `path` (no query string values beyond keys), `status` int nullable, `debug_id` nullable, `request_id` nullable, `duration_ms` int, `source` text `client` or `toolkit`, `created_at`). Written by the client's `logger` hook and the toolkit wrapper. Never request or response bodies, never tokens. Pruned after 30 days with the events prune |
| Ledger read | New ledger read `clearingMovements(db, { from, to })` → each journal touching `paypal:clearing` in the window: journal id, kind, ref type/id, net cents on `paypal:clearing`, created_at, and the PayPal id it belongs to (topup → `topups.capture_id`; bounty capture → `escrows.capture_id`; withdrawal → `payouts.item_id`; clawback → refund id from its idempotency key) — the join lives in the module that owns each table, so expose small lookups from `payments`/`escrow` and combine in `treasurer` |
| Reconciliation | `treasurer/reconcile.ts` `reconcilePayPal(db, { days = 7 })`: matches ledger movements with PayPal transactions (`transaction_info.transaction_id`, amount, `transaction_event_code`) by PayPal id. Classes: `matched`, `missing_in_paypal`, `missing_in_ledger`, `amount_mismatch`, `pending` (ledger side newer than 3 h — PayPal's transaction search lags). Result `{ checkedAt, window, counts, lines[] }`; cached 15 min in memory per process. Only PayPal transactions whose ids we know (or that carry our `custom_id` prefixes `topup:`/`bty_`) count as `missing_in_ledger`; unrelated sandbox account activity is ignored and counted separately as `unrelated` |
| Admin routes | Under the existing admin check: `GET /v1/admin/paypal/calls?cursor` (newest first, 100/page), `GET /v1/admin/paypal/webhooks?cursor` (`webhook_events` without payload bodies: id, paypal event id, type, received/processed, error), `POST /v1/admin/reconcile/paypal { days? }` (runs or returns cached; `?fresh=true` bypasses cache). 503 `paypal_not_configured` when PayPal isn't configured |
| Treasurer agent | `treasurer/agent.ts` `askTreasurer(db, cfg, question)`: tool loop through the gateway (`primary`, OpenAI tool-call format, at most 6 tool calls, 20 s per call, the existing `llm` client and budget; new `llm_calls` role `treasurer`). Tools: `find_payee(name)` → users/agents matching a name or email, `payouts_for(userId)`, `topups_for(userId)`, `bounty_money(bountyId)` (escrow + capture + reward settle), `get_order(orderId)` (toolkit), `get_capture(captureId)`, `list_transactions(days)` (toolkit, at most 7 days), `ledger_for(refType, refId)`, `reconcile_paypal(days)`. Every tool result goes back to the model wrapped with `wrapUntrusted` (PayPal and user text can carry free text) and the system prompt says so. The final answer must cite the ids it relied on; returned with the tool trace `[{ tool, args, ok, summary }]` (summaries, not raw bodies) |
| No LLM | When the gateway is unset or the call fails: a fixed report — if the question names a known user/agent/bounty (simple matching), return its payouts, top-ups and bounty money as a plain table; otherwise "The Treasurer needs the LLM gateway; here is this week's PayPal reconciliation" with the reconcile counts. Never a guessed answer |
| Route | `POST /v1/admin/treasurer/ask { question (1–500 chars) }` → `{ answer, cited: string[], trace, model, fallback: boolean }`. Admin only. Rate limit: 10 asks per minute per admin |
| Web | Admin tabs: new **Treasurer** tab (question box, suggested questions "Why hasn't Scout's owner been paid?", "Does the ledger match PayPal this week?", "What happened to the last top-up?"; answer and cited ids as plain text; collapsible tool trace); **PayPal** tab (AG Grid of PayPal calls and of webhook events); Reconciliation tab gains a "PayPal" card with counts and a "Run against PayPal" button, mismatch lines listed below |
| Fake PayPal | `tests/e2e/fake-paypal.mjs` gains `GET /v2/checkout/orders/:id`, `GET /v2/payments/captures/:id`, `GET /v1/reporting/transactions` built from what it has seen (captures, payouts), so e2e reconcile can be green |

## Changes made during the build

- **Toolkit wrapper.** `paypal/toolkit.ts` loads `@paypal/agent-toolkit/openai` lazily (dynamic import) and builds a fresh `PayPalAgentToolkit` per call with only `orders.get` and `transactions.list` enabled, `context: { sandbox: true, request_id }`. `checkApiBase` (new, in `client.ts`) refuses anything but the sandbox base or a loopback fake, for both the client and the toolkit. The toolkit reports failures as JSON (`{ ok: false, status, … }` or `{ error }`), which the wrapper turns into a `PayPalError` (status 0 when unknown). Toolkit rows in `paypal_calls` carry the request id we generated and status 200 / the toolkit's error status; `debug_id` is always null (the toolkit doesn't expose headers). On a loopback base the same two reads go through the typed client and are logged as `source: client`. `configurePayPalToolkit` / `requirePayPalToolkit` mirror the client instance; `server.ts` configures both. Tests inject a fake toolkit (`makeToolkit`); **the real toolkit was not called** (no PayPal from this sandbox).
- **Direct reads** in `paypal/reads.ts`: `getCapture`, `getAuthorization`, `getPayoutItem`, `listTransactionsDirect` (`transaction_status=S`, `fields=transaction_info`, `page_size=500`), and `toTransactionPage`, which parses both the direct answer and the toolkit's. Signed reporting amounts use the new `signedValueToCents`.
- **Call log.** The client's `logger` hook is now awaited (a throw is ignored) and its entry gained `durationMs`, so a row exists once the call returns. `paypalCallLogger(db, onError)` writes rows; paths keep query keys only (`redactPath`). Network errors are `status: null`. Rows are pruned by `pruneEvents` (it now also returns `paypalCalls`).
- **Ledger reads.** `clearingMovements` returns net cents per journal on `paypal:clearing` plus the idempotency key (clawbacks carry the refund id there); `journalsForRef` backs the `ledger_for` tool. Lookups live with their tables: `payments/lookups.ts` (top-ups, payouts, capture/item ids, known ids, webhook list), `escrow/lookups.ts`, `identity/lookup.ts` (`findPayees`, `payeeDirectory`), `arena/lookups.ts` (`bountyMoneyFacts`).
- **Reconciliation details.** Lines are grouped by PayPal id (a refund is its own id). Dev credits (`refType dev_credit`, or none) and dev escrows are skipped. A denied capture's clawback (`clawback:denied:{captureId}`) maps to the capture id and nets to zero → matched. A movement that should have a PayPal id but has none is listed under `journal:{id}` (pending or missing_in_paypal). The ledger side looks back one extra day so a PayPal transaction near the window's start still finds its journal; ledger-only lines from that day aren't judged. `pending` applies only when PayPal has no transaction. `ok` is false only for missing/mismatch. Up to 10 search pages, 500 lines. Cache is keyed by `days`. The search sends `end_date` rounded up to the next whole second (PayPal takes whole seconds), so a capture in the last second is not cut off.
- **Unverified against real PayPal:** that a payout's transaction-search `transaction_id` equals the payout item id (spec decision; if PayPal uses a different activity id, withdrawals will show as missing_in_paypal plus unrelated activity), and the exact sandbox event codes. The toolkit's list_transactions always sends `transaction_status=S`, so pending captures are invisible to it.
- **503s.** `GET /v1/admin/paypal/calls`, `GET /v1/admin/paypal/webhooks` and `POST /v1/admin/reconcile/paypal` answer 503 `paypal_not_configured` without PayPal (read literally from the Decisions row). `POST /v1/admin/treasurer/ask` still answers without PayPal (fallback says the reconciliation couldn't run). A PayPal failure during reconcile is 502 `paypal_error`. `POST /v1/admin/reconcile/paypal` takes a JSON body (`{}` allowed); `days` max 31. The calls cursor is the last row id.
- **Gateway tool calls.** New `llm/tools.ts` `chatWithTools` (OpenAI `tools` / `tool_choice`, same budget and `llm_calls` logging, no JSON repair). The fake gateway can answer with `toolCalls`. The loop: at most 6 tool calls run (extra calls in a turn get a "not run" tool message); once the cap is hit the next request is sent with `tool_choice: "none"`; a model that still asks for tools, or any failed request (over budget, timeout, error), gets the fallback report, keeping the trace so far. The final reply is `{"answer", "cited"}` JSON; `cited` keeps only ids some tool returned (else the known ids the answer text mentions). Tool results are JSON (cents as integers) wrapped with `wrapUntrusted("tool_<name>", …)` and capped at 12 000 chars. The admin's question is not wrapped (admin input). `model` is the served model.
- **Fallback matching.** Users by id, email or whole-word name; agents by id or whole-word name (→ owner); bounties by `bty_` id; "last/latest top-up" and "last payout/withdrawal" → the newest row. At most 3 users and 3 bounties, 5 rows each, plain-text lines. Otherwise the reconcile counts plus up to 10 problem lines.
- **Rate limit** reuses the demo module's in-memory `RateLimiter` (per api instance, keyed by admin user id); requests rejected by validation don't count.
- **Web.** Tabs order: Journals, Accounts, Reconciliation, PayPal, Treasurer, LLM usage, Demo. The PayPal reconcile card runs only on click (first run may return the cached report; later clicks pass `fresh=true`); states idle / ok / mismatch / error; non-matched lines in a table below the counts. The Treasurer answer renders in a `whitespace-pre-wrap` text node (never HTML/Markdown); the trace is a `<details>`.
- **Fake PayPal** also answers `GET /v2/payments/authorizations/:id` and `GET /v1/payments/payouts-item/:id`. Its transaction search lists captures (status S) and payout items (status P, since the fake never completes items), filtered by date and `transaction_status`.
- **e2e** `tests/e2e/treasurer.spec.ts` tops up through the api (not the browser button, which `paypal.spec.ts` already covers) and asks the fallback a question naming the demo owner's email.
